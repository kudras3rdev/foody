# Foody: требования и архитектура

Oct 24, 2026 · @Dmitry Bulakh

## Назначение и цели качества

Foody — личный счётчик КБЖУ для одного пользователя: фото или подпись еды превращаются в запись с КБЖУ, точность учёта ±10% за день. Это не продукт для рынка: приоритеты — точность и минимум действий, а не охват и монетизация.

**Профиль пользователя и рациона**

- Цель: набор массы и учёт питания.
- Готовит редко; основной рацион — сетевые заведения (Додо, «Вкусно и точка») и товары из магазинов («Пятёрочка», «Перекрёсток»): готовая еда, напитки, энергетики.
- Кухонных весов нет и на старте не будет; напольные весы есть, взвешивание пару раз в неделю.
- Устройство: Android, Samsung S24.

**Цели качества**

| Цель | Значение |
| --- | --- |
| Погрешность дневного итога по калориям | ≤ 10% для дней из 🟢-записей |
| Чтение этикеток | цифры КБЖУ верны после проверок и одного подтверждения |
| Опознание позиции из каталога | ≥ 90% верно с первой попытки |
| Действий на запись | фото (+ подпись по желанию), для 🟢 без подтверждения |

**Подход к точности.** По фото нельзя надёжно оценить вес и скрытые ингредиенты, поэтому распознавание — это сопоставление с личным каталогом позиций с известным КБЖУ (этикетка, официальное меню сети). КБЖУ считает код, а не LLM. Систематическую ошибку учёта ловит тренд веса тела: если по учёту профицит, а вес стоит, учёт врёт.

**Уровни достоверности записи**

- 🟢 Данные этикетки или официального меню, порция стандартная или указана.
- 🟡 Позиция опознана по фото, порция оценена.
- 🔴 Оценка неизвестного блюда (кафе, столовая), погрешность 25–40%.

## Границы проекта

MVP закрывает ежедневный учёт с фото, каталог и контроль по весу; всё «умное» поверх истории откладывается.

| Фаза | Что входит |
| --- | --- |
| MVP | фото + подпись, этикетки и штрихкоды, каталог (Додо, «Вкусно и точка», товары «Пятёрочки» и «Перекрёстка»), уточнение порции, правка, уровни достоверности, «повторить» и избранное, дневная сводка, ручной ввод веса и тренд, полная история, экспорт |
| После MVP | справочник для неизвестных блюд (Скурихин, USDA, Open Food Facts), подсказки по корректировке цели по тренду веса, напоминания, рецепты, кухонные весы, Health Connect, теневой режим моделей, советы и планы питания |
| Вне рамок | вода, микронутриенты, социальные функции, публикация в магазинах приложений; многопользовательский режим не делается, но архитектура его не блокирует |

## Функциональные требования

Все требования ниже относятся к MVP; критерий приёмки — как проверить, что требование выполнено.

| ID | Требование | Критерий приёмки |
| --- | --- | --- |
| FR-01 | Захват приёма пищи: фото и необязательная подпись (текст или голос через распознавание речи Android) | запись создаётся одним действием с главного экрана, плитки или виджета |
| FR-02 | Захват без фото: только текст («додо пепперони 3 куска») | текстовая запись проходит тот же конвейер |
| FR-03 | Сканирование штрихкода на устройстве | известный товар добавляется без обращения к LLM |
| FR-04 | Добавление товара по фото этикетки: извлечение КБЖУ на 100 г или 100 мл и размера упаковки | данные проходят проверки FR-05 и сохраняются в каталог |
| FR-05 | Проверки этикетки: формула 4·Б + 9·Ж + 4·У сходится с калорийностью в пределах max(15%, 5 ккал); Б+Ж+У ≤ 100 г на 100 г (мл); калорийность ≤ 900 ккал на 100 г (мл); при двух моделях — сверка | не прошедшая проверку этикетка уходит на подтверждение |
| FR-06 | Опознание еды по фото и подписи с приоритетом позиций из каталога | ответ содержит позицию каталога или новую позицию с оценкой |
| FR-07 | Каталог позиций: товары, позиции сетей, оценённые блюда; пополняется автоматически при каждом новом продукте | повторная встреча позиции не требует повторного распознавания этикетки |
| FR-08 | Стартовое наполнение каталога меню Додо и «Вкусно и точка» с официальным КБЖУ | позиции доступны до первого использования |
| FR-09 | Уточнение количества: целиком, половина, N штук или кусков, граммы | одно нажатие для типовых вариантов |
| FR-10 | Уровень достоверности у каждой записи (🟢🟡🔴) и доля калорий из 🔴 в сводке дня | видно в записи и в сводке |
| FR-11 | Подтверждение: 🟢 сохраняется сразу с возможностью отмены; 🟡 и 🔴 показываются с кнопками «верно» и «изменить» | 🟢 не требует действий |
| FR-12 | Правка записи: позиция, количество, добавка («+масло 10 г»), удаление | правка пересчитывает итоги |
| FR-13 | Быстрый повтор: недавние, избранное, «как вчера» | запись повтора — одно-два нажатия |
| FR-14 | Цели по калориям и белку задаются вручную | сводка показывает съедено и осталось |
| FR-15 | Дневная сводка: ккал, Б, Ж, У против цели; список записей по времени, без деления на приёмы пищи | на главном экране |
| FR-16 | Ручной ввод веса тела и график тренда (скользящее среднее) | тренд за 7 и 30 дней |
| FR-17 | Полная история: исходное фото, ответ модели, правки пользователя, итоговая запись | любая запись восстанавливается до исходных данных |
| FR-18 | Пересчёт: повторная обработка выбранных записей другой конфигурацией моделей | результат сохраняется отдельно, не затирая исходный |
| FR-19 | Экспорт всех данных (JSON или CSV + фото) | полный экспорт одной командой |
| FR-20 | Eval: прогон золотого набора через конфигурацию моделей с отчётом по метрикам | CLI-команда выдаёт таблицу точности, задержки и цены |

## Нефункциональные требования

Главные НФТ — скорость захвата, устойчивость к плохой сети и сменяемость моделей.

| ID | Категория | Требование |
| --- | --- | --- |
| NFR-01 | Скорость | от нажатия до камеры < 2 с (плитка, ярлык, виджет) |
| NFR-02 | Скорость | фото принято приложением < 1 с, независимо от сети |
| NFR-03 | Скорость | результат распознавания < 15 с в 95% случаев при наличии сети |
| NFR-04 | Надёжность | офлайн-очередь: фото и записи не теряются без сети и отправляются при её появлении |
| NFR-05 | Надёжность | обработка асинхронная и идемпотентная: повтор отправки не создаёт дублей |
| NFR-06 | Надёжность | бэкап базы и фото ежедневно, вне сервера |
| NFR-07 | Сменяемость моделей | модели и провайдеры задаются конфигом; замена или добавление модели без изменения кода задач |
| NFR-08 | Сменяемость моделей | fallback-цепочка на задачу: при ошибке, 429 или невалидном ответе запрос уходит следующей модели |
| NFR-09 | Наблюдаемость | журнал каждого вызова модели: провайдер, модель, версия промпта, задержка, токены, стоимость, сырой ответ |
| NFR-10 | Корректность | ответы моделей валидируются по схеме; система не принимает невалидный JSON |
| NFR-11 | Ресурсы | бэкенд работает на VPS 1 ядро, 2 ГБ RAM, 30 ГБ SSD; фото ≤ 1024 px по длинной стороне, сжатие на телефоне |
| NFR-12 | Стоимость | на старте только бесплатные уровни API; целевой потолок платного режима — несколько долларов в месяц |
| NFR-13 | Безопасность | только HTTPS; доступ по токену; все данные привязаны к user\_id для будущей многопользовательности |
| NFR-14 | Сопровождаемость | бизнес-логика на сервере (Go), клиент тонкий; это снижает объём Kotlin-кода, написанного через AI |

## Ограничения и принятые решения

**Ограничения**

- C-01. Пользователь в РФ: Telegram замедляется, зарубежные LLM API из РФ напрямую недоступны.
- C-02. Сервер: VPS в Финляндии, 1 ядро, 2 ГБ RAM, 30 ГБ SSD; локальные vision-модели невозможны.
- C-03. Клиент только Android (Samsung S24).
- C-04. Опыт разработчика: Go-бэкенд; мобильная разработка через вайбкодинг.
- C-05. Бюджет на модели: старт на бесплатных уровнях, иностранная карта есть для перехода на платные.

**Решения**

| ID | Решение | Отклонённые варианты | Причина |
| --- | --- | --- | --- |
| D-01 | Нативный Android-клиент (Kotlin + Jetpack Compose) | Telegram-бот, бот в MAX, PWA | 1 тап до камеры, штрихкод на устройстве (ML Kit), офлайн-очередь, виджет; Telegram замедляет загрузку медиа |
| D-02 | Бэкенд на Go на финском VPS | — | основной стек; сервер вне РФ даёт доступ к LLM API без VPN на телефоне |
| D-03 | SQLite (WAL) + фото на диске | Postgres | один пользователь, 2 ГБ RAM, бэкап = копия файла |
| D-04 | Распознавание = сопоставление с каталогом; КБЖУ считает код | LLM считает КБЖУ сама | LLM галлюцинирует цифры; каталог даёт точность этикетки |
| D-05 | Абстракция на уровне задач (MealRecognizer, LabelExtractor), а не LLM | единый LLMClient | задачи на разных моделях, часть без LLM |
| D-06 | Один OpenAI-совместимый адаптер, нативные — по необходимости | адаптер на каждого провайдера | Gemini, Mistral, Groq, OpenRouter поддерживают совместимый API |
| D-07 | Толстый сервер, тонкий клиент | логика на клиенте | Go-код проверяем сам; Kotlin-код минимален |
| D-08 | Токен-аутентификация, user\_id во всех таблицах | регистрация, OAuth | один пользователь сейчас, расширение без миграции схемы |
| D-09 | Выбор моделей по eval на золотом наборе | выбор по отзывам | решение по цифрам на своей еде |

**Стартовая гипотеза по моделям** (проверяется eval):

| Задача | Основная | Запасная |
| --- | --- | --- |
| Чтение этикетки | Gemini Flash | Mistral (и как вторая модель для сверки) |
| Опознание из каталога | Gemini Flash-Lite | Groq Llama 4 |
| Разбор текста | Groq Llama 4 | Gemini Flash-Lite |
| Неизвестное блюдо (ветка опознания, ADR 002) | GPT-4o или бесплатная vision-модель через OpenRouter (ADR 005) | Gemini Flash |

## Архитектура: компоненты и потоки

Клиент только снимает, ставит в очередь и показывает; распознавание, каталог и подсчёт живут на сервере, модели — внешние.

Схема компонентов и потоки: [architecture.md](architecture.md), разделы 2–3.

Офлайн-очередь отправляет запись в API (загрузка), экраны получают результаты через синхронизацию. Воркер запускает задачи распознавания; задачи вызывают модели через реестр (конфиг, fallback, журнал), а КБЖУ считает каталог кодом. Eval, пересчёт и сид каталога — CLI на том же сервере.

## Жизненный цикл записи

Запись — конечный автомат с шестью состояниями; в сводку дня попадает только confirmed.

Диаграмма и таблица переходов: [architecture.md](architecture.md), раздел 6.

Из любого состояния запись можно удалить (мягко, с отменой). Правка confirmed оставляет её в confirmed, пишет entry\_edits и пересчитывает сводку. Пересчёт другой конфигурацией моделей создаёт новый recognition\_run и не меняет состояние записи.

## Модель данных (черновик)

Запись о еде хранит снимок КБЖУ на момент подтверждения: правка каталога не меняет историю молча, пересчёт делается явно (FR-18).

| Сущность | Ключевые поля | Назначение |
| --- | --- | --- |
| users | id, name, token\_hash, created\_at | задел под многопользовательность |
| goals | user\_id, kcal, protein\_g, valid\_from | цели с историей изменений |
| catalog\_items | id, user\_id (NULL = общий сид), kind (packaged, chain\_menu, estimated\_dish), name, brand, barcode, basis (g, ml), kcal/p/f/c на 100 единиц базы, pack\_size, portions (JSON: «кусок» = 110 г), source (label, official\_menu, llm\_estimate, manual), verified, aliases | личный каталог позиций |
| photos | id, user\_id, sha256, path, width, height, taken\_at | исходные фото на диске |
| meal\_entries | id (UUID с клиента), user\_id, eaten\_at, caption, photo\_id, status, confidence, created\_at, updated\_at, deleted\_at | запись о приёме пищи |
| entry\_items | id, entry\_id, catalog\_item\_id, quantity, unit, amount (г или мл по basis позиции), amount\_source (label, menu, estimate, user, scale), kcal/p/f/c (снимок) | строки записи: из чего состоит приём |
| recognition\_runs | id, entry\_id, task, config\_version, result\_json, status, is\_active, created\_at | каждый прогон распознавания, включая пересчёты |
| model\_calls | id, run\_id, provider, model, prompt\_version, latency\_ms, tokens\_in, tokens\_out, cost\_usd, status, error, raw\_response | журнал вызовов моделей (NFR-09) |
| entry\_edits | id, entry\_id, before\_json, after\_json, created\_at | правки пользователя — личный датасет ошибок модели |
| body\_weights | id, user\_id, measured\_at, kg | вес тела для тренда |
| eval\_cases | id, photo\_id, caption, kind, expected\_json | золотой набор для eval |

UUID записи генерирует клиент: это делает повторную отправку из офлайн-очереди идемпотентной (NFR-05).

## API (черновик)

REST + JSON поверх HTTPS, заголовок `Authorization: Bearer <token>`, префикс `/v1`. Загрузка фото возвращает 202 сразу, распознавание идёт в фоне.

| Метод и путь | Назначение |
| --- | --- |
| `POST /v1/entries` | создать запись: multipart (id, eaten\_at, caption, photo) → 202 + статус |
| `GET /v1/entries/{id}` | запись со строками, статусом и уровнем достоверности |
| `GET /v1/entries?date=YYYY-MM-DD` | записи за день |
| `PATCH /v1/entries/{id}` | правка строк: позиция, количество, добавки |
| `POST /v1/entries/{id}/confirm` | подтвердить 🟡 или 🔴 запись |
| `DELETE /v1/entries/{id}` | удалить (мягко, с возможностью отмены) |
| `POST /v1/entries/{id}/repeat` | повторить запись на текущее время |
| `GET /v1/catalog/search?q=` | поиск по каталогу для ручного выбора |
| `GET /v1/catalog/barcode/{code}` | позиция по штрихкоду или 404 |
| `POST /v1/catalog/labels` | фото этикетки → 202, новая позиция после проверок |
| `GET /v1/summary?date=` | дневная сводка против цели, доля 🔴 |
| `GET` / `PUT /v1/goals` | цели по калориям и белку |
| `POST /v1/weights`, `GET /v1/weights?from=&to=` | вес тела и тренд |
| `GET /v1/sync?since=<cursor>` | изменения с курсора для локального кэша клиента |
| `GET /v1/export` | полный экспорт |

О готовности распознавания клиент узнаёт опросом с нарастающей паузой, пока экран открыт; push через FCM — после MVP. Eval, пересчёт истории и загрузка сида каталога — CLI-команды бэкенда, не HTTP.

## Риски, открытые вопросы, глоссарий

**Риски**

| Риск | Влияние | Что делаем |
| --- | --- | --- |
| Бесплатные уровни урезают или меняют условия | распознавание перестаёт работать | fallback-цепочки (NFR-08), переход на платные — смена конфига |
| Условия Gemini для ЕС и неподдерживаемого региона пользователя | блокировка ключа | Mistral и OpenRouter в цепочке; платный уровень как запасной путь |
| Ошибка чтения этикетки попадает в каталог | систематическая ошибка во всех будущих записях | проверки FR-05, сверка двумя моделями, подтверждение при первом добавлении |
| Систематическая недооценка блюд в кафе | недобор при наборе массы | метка 🔴, доля 🔴 в сводке, контроль по тренду веса |
| Kotlin-код через вайбкодинг сложно проверять | баги на клиенте | тонкий клиент (D-07), стандартный стек Google, простые экраны |
| Зарубежный VPS недоступен у мобильного оператора | приложение не может отправить данные | офлайн-очередь (NFR-04); проверить доступность до старта |

**Открытые вопросы**

- [ ] Источник официального КБЖУ для сида Додо и «Вкусно и точка»: сайт, приложение или ручной ввод.
- [ ] Хранение фото: сколько держать оригиналы при 30 ГБ (оценка < 1 ГБ в год — вероятно, всё).
- [ ] Формат бэкапа и куда: объектное хранилище, второй сервер или домашний компьютер.
- [ ] Как вести золотой набор: отдельный режим в приложении или пометка обычных записей.

**Глоссарий**

- Позиция каталога — продукт или блюдо с КБЖУ на 100 г или 100 мл (база `basis`) и типовыми порциями.
- Запись — один приём пищи: время, фото, подпись и строки с позициями.
- Прогон распознавания — один проход конвейера по записи с конкретной конфигурацией моделей.
- Конфигурация моделей — набор «задача → цепочка моделей + версия промпта».
- Золотой набор — фото с известным правильным ответом для eval.
