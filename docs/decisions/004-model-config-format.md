# 004. Формат и загрузка конфига моделей

## Контекст

Модели, цепочки и промпты задаются в `backend/config/models.yaml` (NFR-07, D-05). В стандартной библиотеке Go нет YAML. Кроме того, не было определено, от какого каталога считаются пути к промптам, где хранится цена модели для метрики стоимости в eval (FR-20) и какой таймаут ставится, если он не указан.

## Решение

1. Зависимость `go.yaml.in/yaml/v3`. Это поддерживаемое продолжение `gopkg.in/yaml.v3`: оригинал заархивирован, а форк ведёт организация YAML. Библиотека чистый Go без транзитивных зависимостей. Она понадобится и для `data/golden/cases.yaml`.
2. Конфиг читается строго: неизвестное поле (опечатка) — ошибка. Все ошибки валидации возвращаются одним списком с путём до поля (`tasks.meal_recognition.chain[0].provider`).
3. Относительные пути к промптам считаются от каталога конфига. Из `backend/config/models.yaml` это `../prompts/meal_v1.md`. Так результат не зависит от текущего каталога при запуске.
4. Имя файла промпта обязано содержать версию (`<имя>_v<N>.md`). Версия промпта = имя файла без расширения.
5. У звена цепочки есть необязательные поля `timeout` (по умолчанию 30s) и `price: { input, output }` — доллары за 1M токенов, по умолчанию 0 для бесплатных уровней.
6. Версия задачи (`recognition_runs.config_version`) — первые 12 hex-символов SHA-256 от версии и текста промпта, флага сверки и списка «провайдер/модель». Таймауты и цены в хэш не входят: на результат они не влияют.
7. Ключи API при загрузке не проверяются: конфиг валиден и без ключей, ключ читается из окружения при вызове модели.

## Альтернативы

- **JSON вместо YAML (только стандартная библиотека).** Отклонено: в JSON нет комментариев, а конфиг правится руками и комментируется. К тому же YAML всё равно нужен для золотого набора.
- **`gopkg.in/yaml.v3`.** Отклонено: репозиторий заархивирован, исправления выходят только в форке.
- **Пути от текущего каталога.** Отклонено: `foody eval` из корня репозитория и из `backend/` находил бы разные файлы.
