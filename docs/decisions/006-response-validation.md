# 006. Проверка ответов моделей: Go-типы вместо JSON Schema

## Контекст

NFR-10 требует, чтобы ответ модели проверялся по схеме и невалидный JSON дальше не проходил. architecture.md (5.3) говорит о «JSON Schema задачи» с одним повтором той же модели. В стандартной библиотеке Go нет валидатора JSON Schema. Кроме того, задаче всё равно нужен ответ в виде Go-структуры.

## Решение

1. Схема задачи — это Go-тип результата и его метод `Validate() error` с правилами, которые не выражаются типом: обязательные поля (через указатели), «ровно одно из `catalog_item_id` и `new_item`», диапазоны.
2. `llm.DecodeJSON[T]` разбирает строго: ровно один JSON-объект, неизвестные поля и несовпадение типов — ошибка, затем вызывается `Validate()`. Допускается одна обёртка ```` ```json … ``` ````, которую модели добавляют даже в JSON-режиме; любой другой текст вокруг JSON — ошибка.
3. При невалидном ответе реестр повторяет ту же модель один раз. К исходным сообщениям добавляются её ответ (`assistant`) и текст ошибки (`user`). Если и повтор невалиден, запрос уходит следующей модели. Повтор пишется в журнал отдельной попыткой с `retry = true`, поэтому eval может посчитать долю валидных ответов с первой попытки.
4. Текст сообщения для повтора — константа в `internal/llm/registry.go`, а не файл в `prompts/`. Это сознательное исключение из правила «промпты только в `prompts/`»: сообщение техническое и не зависит от задачи. Если оно начнёт влиять на качество, переносим его в `prompts/`, и оно войдёт в версию задачи.

## Альтернативы

- **Библиотека JSON Schema (например, `santhosh-tekuri/jsonschema`).** Отклонено: новая зависимость и два описания одного контракта, схема и Go-тип, которые нужно держать в согласии. Плюс схемы — её можно вставить в промпт; но пример JSON в промпте для моделей понятнее.
- **Мягкий разбор: искать JSON внутри любого текста.** Отклонено: прячет плохие ответы и портит метрику валидности в eval.
