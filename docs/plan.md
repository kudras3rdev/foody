# Foody: план MVP

Требования: [requirements.md](requirements.md). Архитектура: [architecture.md](architecture.md).

**Текущий этап: 0 и 1** (сбор данных и ядро моделей идут параллельно).

Порядок выбран так, чтобы главный риск проекта — «насколько хорошо модели распознают мою еду» — закрылся первым и дешевле всего, до написания приложения.

| Этап | Результат | Оценка |
|---|---|---|
| 0. Данные | золотой набор 50–80 фото с эталонами | 1 неделя, параллельно с этапом 1 |
| 1. Ядро моделей и eval | отчёт по 3–4 моделям, выбрана стартовая конфигурация | 2–4 вечера |
| 2. Бэкенд MVP | учёт ведётся через curl или CLI, сервер работает на VPS | 1–2 недели |
| 3. Android MVP | ежедневный учёт с телефона | 1–2 недели |
| 4. Удобство | «фото → готово» за 2 нажатия, тренд веса | 1 неделя |

## Этап 0. Сбор данных

Без кода. Цель — набор фото с известным правильным ответом для eval.

- [ ] Неделю фотографировать всё, что ешь и пьёшь, обычной камерой
- [ ] Отдельно фотографировать этикетки (таблицу КБЖУ) новых товаров
- [ ] Для каждого фото записать эталон в `data/golden/cases.yaml`
- [ ] Получить ключи API: Gemini, Mistral, Groq, OpenRouter (GitHub Models закрыт, ADR 005)

Состав набора (ориентир):

| Тип | Количество | Откуда эталон |
|---|---|---|
| этикетки товаров | ~25 | цифры с упаковки |
| позиции Додо, «Вкусно и точка» | ~20 | официальное меню сети |
| напитки (кола, энергетики) | ~10 | этикетка |
| кафе и неизвестные блюда | ~10 | приблизительная оценка, для сравнения моделей между собой |

Формат `cases.yaml` (цифры в примере условные):

```yaml
- id: "001"
  photo: "001.jpg"
  kind: label                 # label | meal
  caption: ""                 # подпись, как ты написал бы её в приложении
  expected:
    name: "Йогурт Активиа клубника"
    basis: g                  # g | ml (напитки — ml), ADR 001
    per_100: { kcal: 79, protein: 2.8, fat: 2.4, carbs: 11.5 }
    pack_size: 150            # в единицах basis

- id: "014"
  photo: "014.jpg"
  kind: meal
  caption: "додо пепперони 3 куска"
  expected:
    items:
      - name: "Додо Пепперони 30 см, кусок"
        quantity: 3
        unit: piece
        kcal_total: 810       # из меню сети
    confidence_expected: high # какой уровень должен получиться

- id: "041"
  photo: "041.jpg"
  kind: meal
  caption: ""
  expected:
    items:
      - name: "Плов, столовая"
        amount_approx: 300    # в единицах basis позиции
        kcal_total_approx: 500
    exact: false              # эталон приблизительный
```

**Готово, когда:** в наборе ≥ 50 случаев, у каждого заполнен `expected`.

## Этап 1. Ядро моделей и eval

Цель — выбрать модели по цифрам. Без HTTP API, без БД записей, без Android.

- [x] Каркас репозитория: `backend/` с Go-модулем, `cmd/foody`, `.env.example`, `.gitignore` для `data/`
- [x] Загрузка и валидация `config/models.yaml` (NFR-07)
- [x] OpenAI-совместимый клиент с поддержкой изображений (D-06)
- [x] Реестр моделей: fallback-цепочка, правила перехода, таймауты (NFR-08)
- [x] Валидация ответа по схеме задачи (ADR 006), повтор с текстом ошибки (NFR-10)
- [x] Журнал вызовов в JSONL (БД появится на этапе 2) (NFR-09)
- [x] `LabelExtractor` + промпт `label_v1` + проверки 4/9/4 и диапазонов (FR-04, FR-05)
- [ ] `MealRecognizer` + промпт `meal_v1`; кандидаты пока из файла с позициями набора
- [ ] CLI `foody eval` (FR-20): прогон каждой модели отдельно, метрики, JSON-отчёт
- [ ] Прогон на наборе, выбор основной и запасной модели для каждой задачи
- [ ] Короткий ADR в `docs/decisions/` с результатами eval и выбором моделей

**Готово, когда:** есть отчёт eval по 3–4 моделям и записан выбор моделей.

**Критерии выбора:**
- этикетки: все поля верны в ≥ 95% случаев до проверок; ошибки, прошедшие проверки, — 0;
  - «все поля» = `basis`, `pack_size`, ккал, Б, Ж, У; поле верно, если прочитано как на упаковке: `basis` и `pack_size` точно, ккал ±0.5, Б/Ж/У ±0.05; название и бренд в «все поля» не входят и оцениваются отдельно;
- опознание с кандидатами: ≥ 90% верно с первой попытки;
- доля невалидных ответов: < 5% (fallback закрывает остальное);
- задержка p95: < 15 с.

**Если модели не дотягивают:** сначала улучшить промпты и подачу кандидатов, затем попробовать платные модели (несколько долларов в месяц), и только потом пересматривать подход.

## Этап 2. Бэкенд MVP

Цель — полноценный серверный учёт без мобильного клиента.

- [ ] SQLite (WAL), встроенные миграции, схема по модели данных
- [ ] Журнал вызовов моделей переносится из JSONL в `model_calls`
- [ ] Пользователь и токен-аутентификация (D-08, NFR-13)
- [ ] Каталог: позиции, поиск, штрихкоды, кандидаты для опознания (FR-07)
- [ ] CLI `foody seed`: меню Додо и «Вкусно и точка» с официальным КБЖУ (FR-08)
- [ ] Записи: `POST /v1/entries` (202), чтение, правка, подтверждение, удаление, повтор
- [ ] Воркер и жизненный цикл записи по таблице переходов (architecture.md, раздел 6)
- [ ] Подсчёт КБЖУ, снимок в `entry_items`, уровень достоверности (FR-10, FR-11)
- [ ] Этикетки через API со сверкой двумя моделями
- [ ] `TextParser` для записей без фото (FR-02)
- [ ] Цели, дневная сводка с долей `low` (FR-14, FR-15)
- [ ] Вес тела и тренд (FR-16)
- [ ] `GET /v1/sync` и `GET /v1/export` (FR-19)
- [ ] CLI `foody reprocess` (FR-18)
- [ ] Деплой на VPS: systemd, HTTPS, `.env`
- [ ] Ежедневный бэкап вне VPS (NFR-06)
- [ ] Проверка доступности сервера с мобильного интернета оператора

**Готово, когда:** день учёта целиком проходит через API (curl или CLI), данные переживают перезапуск и восстанавливаются из бэкапа.

## После MVP

В порядке ожидаемой пользы:

1. Подсказка корректировки цели по тренду веса
2. Справочник для неизвестных блюд (Скурихин, USDA, Open Food Facts)
3. Теневой режим моделей: вторая модель на реальных записях
4. Push через FCM вместо опроса
5. Напоминания о пропущенных приёмах пищи
6. Рецепты и составные блюда
7. Кухонные весы как источник граммовки
8. Синхронизация веса через Health Connect
9. Советы и планы питания по истории
